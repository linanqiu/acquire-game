## Context

Owner (2026-11-16): "Can you make trading with the rules based bots smarter? They trade valuable
assets at face value without considering majority minority etc. Also write this into the LLM
strategy guide."

The bot accepted any offer worth more at current share prices, so its majority in a chain, or the
shares deciding a coming merger bonus, could be bought for list price. Formula, example,
self-play numbers and limits: [docs/ai/bot-trading.md](../../../ai/bot-trading.md).

## Acceptance criteria

- [x] One pure valuation function (`game/trade_value.py: trade_valuation`), public information
      only, reusing the calculator helpers and `Rules.calculate_bonuses`: cash and shares at
      current prices, expected bonus value per active chain (weight 0.9 for a chain that can still
      be absorbed, 0.5 -> 0.9 with game progress for a safe one), the change in majority/minority
      standing for both sides, little value for a chain off the board, a 10 % premium for shares
      the bank has run out of, and a counterparty effect (the proposer's gain counts against the
      trade, in full when the proposer is ahead). Plain JSON-serialisable dict.
- [x] The calculator pack carries it (`calc["trades"][trade_id]`) for every open offer the viewer
      is a party to.
- [x] The bot accepts only a valid trade whose adjusted gain is positive and clears the margin
      (5 % of the trade's size, 10 % when the proposer is ahead); deterministic; same
      `apply_action` path as every seat; it still never proposes.
- [x] Tier 1 (`tests/test_trade_value.py`, real-play positions): majority and minority shares at
      face value rejected and at a covering price accepted; no position involved: face value plus
      margin; a share that hands the proposer a majority is priced accordingly; richer versus
      poorer proposer; massive overpayment accepted; cash requested from the bot; share-for-share
      swaps; a stale (invalid) offer is never accepted; sold-out and off-board chains; random
      offers during bot-played games.
- [x] Tier 2 (`tests/protocol/test_trades.py`): a human proposes over the WebSocket, the bot
      rejects list price for its sole majority and accepts a covering price.
- [x] LLM seats: the playbook's "Trade offer" line carries the reasoning (about 110 words,
      theme-neutral); the offer block shows the list-price and position-aware numbers for both
      sides and the positions that change. `PROMPT_BUILDER_VERSION` 6 -> 7.
      `docs/ai/strategy-playbook.md` updated.
- [x] Self-play check: a seat that snipes about-to-be-paid positions at list price + $100 gained
      $16,140 per game over the other seats before (19/30 wins) and $187 now (10/30 wins).
- [x] Generated snapshot fixtures unchanged (`python -m fixtures_gen`); no frontend change, so no
      new surface in the coverage map.

## Notes

- **Where the function lives.** The seat contract lets an agent see only `ctx` (public state,
  legal options, calculator pack), never the game. The valuation needs the engine's bonus rules,
  so it runs where the calculator pack is built and the bot reads the result from the pack. The
  LLM prompt reads the same entry, so both kinds of seat see the same numbers.
- **Deviation:** the brief suggested `game/calculator.py`; the function is in its own module next
  to it (`game/trade_value.py`), because the calculator is already 940 lines. It imports the
  calculator's helpers.
- **Rival weight 0.5 when the proposer is not ahead** (three or more players): a trade that gains
  both sides also gains on everyone else, so the bot asks for at least half of what the proposer
  gains rather than all of it. Two players, or a proposer ahead in net worth: weight 1.0.
- No model calls were made for this story; the effect of prompt v7 on LLM play is not measured.
