# LO-005: Lobby UI for AI Opponents and "Thinking" Indicator

## Metadata
- **Epic**: [LLM Opponents](../../epics/09-llm-bot.md)
- **Status**: `in-progress`
- **Priority**: `high`
- **Effort**: `M` (1-2h)
- **Dependencies**: LO-001 (catalog), ES-005 (`awaiting` in broadcasts)

## Context

Today the lobby offers a single "+ ADD BOT" button (player and host pages). Players need to choose
which AI opponent to add, see who is human or AI, and see when an AI is deciding (LLM calls take
seconds).

## Requirements

- Lobby (both `PlayerPage` lobby and `HostPage` lobby): replace "+ ADD BOT" with an "Add AI" control
  that lists `GET /agents/catalog` entries (label + description). Unavailable entries are shown
  disabled with a reason.
- Add via `POST /room/{code}/add-seat`; remove via `POST /room/{code}/remove-seat/{player_id}`
  (lobby only, AI seats only).
- Player lists show `kind` and `agent_label` (e.g. "Claude - hard").
- In-game: when `awaiting.kind` is `llm` (or any non-human), show a "thinking" indicator naming the
  seat, on both player and host views. Indicator clears when the next state arrives.
- Error states: catalog fetch fails (fall back to a plain "Add bot"), add-seat 4xx (toast).
- Stable `data-testid`s: `add-ai-button`, `add-ai-option-<id>`, `remove-seat-<player_id>`,
  `thinking-indicator`.

## Acceptance Criteria

- [ ] Catalog options render; unavailable ones are disabled.
- [ ] Adding and removing an AI seat updates all connected clients' lobby lists.
- [ ] Thinking indicator appears while an LLM/bot seat is `awaiting` and disappears after it acts.
- [ ] Component tests (Vitest) for the control and indicator.
- [ ] Surface coverage map rows for these surfaces exist and name a test (see TP-006).

## Implementation Notes

- Keep `is_bot` handling for compatibility; prefer `kind` for new code.
- Types: update `frontend/src/types` for `kind`, `agent_label`, `awaiting`.
