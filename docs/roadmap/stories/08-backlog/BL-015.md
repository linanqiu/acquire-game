# BL-015: The merging player picks the order of same-size defunct chains

## Metadata
- **Epic**: Backlog
- **Status**: `completed`
- **Priority**: `high`
- **Effort**: `L` (3+ hours)
- **Dependencies**: ES-001 (decisions API), BL-011 (decision tab), TP-003 (generated fixtures)

## Context

Owner feedback (2026-11-16): "Merger order should be picked."

The rule (standard for this family of games): in a merger of three or more chains the defunct
chains are resolved largest first, and when defunct chains are the **same size** the player who
placed the merging tile chooses which of them is resolved first. The engine sorted by size and
broke ties by board order, without asking. The order is not cosmetic: holders of the chain
resolved first trade 2:1 first, and the survivor's bank stock can run out before the next
chain's holders get their turn.

## Acceptance Criteria
- [x] **Engine**: a new flow decision `choose_defunct_order` for the tile placer whenever two or
      more of the defunct chains still to be resolved share the largest size. It offers exactly
      those chains; chains of a different size are never offered. Answered with the action
      `merger_order` (`defunct_chain`), validated in `game.decisions` like every other action
      and applied through `apply_action`.
- [x] **Multi-way ties are answered one pick at a time**: with three same-size chains the placer
      picks the first, that chain is resolved (bonuses, dispositions), then the placer picks
      between the other two; the last chain needs no pick. Survivor tie plus defunct tie (sizes
      3, 3, 2, 2) works: survivor choice, the other 3 at once, then the pick between the 2s.
- [x] **Event** `defunct_order_chosen` (`chain`, `tied_chains`, `survivor`, `size`); the merger
      history (`game_state.mergers`) lists defunct chains in the order actually used.
- [x] **Snapshot / restore** mid-decision round-trips (the decision lives in `pending_action`;
      no new state).
- [x] **Server**: the deciding human gets `choose_merger_order` (`tied_chains`,
      `surviving_chain`), also on reconnect; `merger_order` is a validated WebSocket / HTTP

- [x] **Seats**: rules bot (documented rule below), scripted seats and fixture policies (first

## Design decisions

- **Name**: decision kind and pending type `choose_defunct_order`; action `merger_order`;
  prompt message `choose_merger_order`; event `defunct_order_chosen` (next to
  `choose_survivor` / `merger_choice` / `choose_merger_survivor` / `survivor_chosen`).
- **One pick at a time, asked when the chain's turn comes** (in
  `MergerMixin._process_next_defunct_chain`), not a full ordering up front. It is the smallest
  change to the merger state machine (no new merger state, so snapshots keep their format), the
  answer is a single chain like the survivor choice, and for a three-way tie the second pick is
  made knowing how the first chain's holders disposed.
- **Bot rule** (`Bot.choose_defunct_order`, all difficulties, no RNG): the tied chain the bot
  holds the most shares of (its holders trade first), then the one that pays the bot the larger
  bonus, then the listed (board) order.
- **Defaults**: scripted seats' default action, the fixture policies and an LLM seat's fallback
  (the rules bot) all answer without the model. There is no timeout for human decisions in this
  server, so none was added. The first listed chain is the old board order.
- **Fixtures**: new `merger-order-tie` (seed 12, 3 players). `multi-chain-merger` changed
  legitimately: its recorded game passes through a same-size defunct pair, so its action list
  and event log gained one `merger_order` / `defunct_order_chosen` (same order as before, same
  final state otherwise). All other fixtures regenerate byte-identical.
  `frontend/tests/unit/fixtures/wire-messages.json` was re-recorded (it embeds every fixture).
