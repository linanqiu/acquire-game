# SH-001: Enforce Session Token Validation

## Metadata
- **Epic**: Security Hardening
- **Status**: `complete`
- **Priority**: `high`
- **Effort**: `S` (30-60m)
- **Dependencies**: GU-016 (E2E tests must pass first)

## Context

Session tokens are currently optional for backward compatibility. The code validates tokens only when both the request and stored token are non-null. This allows connections without any authentication.

```python
# Current behavior in main.py
if token is not None and player_conn.session_token is not None:
    if token != player_conn.session_token:
        # Validate only if both present
```

This needs to be mandatory before production.

## Requirements

1. Make session token required for all player WebSocket connections
2. Require token for all authenticated REST endpoints
3. Update frontend to always send tokens
4. Add tests verifying token enforcement

## Acceptance Criteria

- [x] WebSocket connections rejected without valid session token
- [x] REST endpoints (`/room/{code}/start`, `/room/{code}/add-bot`) require token
- [x] Token returned from `/create` and `/join` endpoints
- [x] Frontend stores and sends token with all requests
- [x] Unauthorized requests return 401 status
- [x] Tests verify token enforcement for all protected endpoints

## Implementation Deviations (2026-07-13)

The story's Context assumed session tokens already existed as "optional". In the
actual code there were **no session tokens at all** (no `session_token` field on
`PlayerConnection`), even though the frontend already stored/sent
`data.session_token` and `?token=` on the player WebSocket URL. Tokens were
therefore added from scratch:

- `PlayerConnection.session_token` (uuid4 hex) generated on join; returned from
  `/create` and `/join`.
- `GameRoom.host_token` generated per room and returned from `/create-spectator`,
  because the spectator flow has no player and still needs to add bots, start
  games, and connect the host WebSocket.
- `/room/{code}/start` and `/room/{code}/add-bot` require
  `Authorization: Bearer <token>` (raw token also accepted); valid tokens are the
  room's host token or any player's session token. Missing/invalid token → 401;
  unknown room stays 404.
- Player WebSocket requires `?token=` matching *that player's* token, else closed
  with 4001. Host WebSocket (`/ws/host/{code}`) also requires a token (host token
  or any player token) since it can add bots / start / end games; the frontend
  spectator flow now stores `host_token` and sends it (see `getHostToken()` in
  `useHostWebSocket.ts`).
- Test-support endpoints `/room/{code}/configure`, `/room/{code}/action/{pid}`,
  and `/room/{code}/refresh/{pid}` were intentionally left unauthenticated: E2E
  scenario helpers call them without tokens, and `player_id` is an unguessable
  uuid4. Follow-up hardening could lock these down.
- Auth failures are logged via `logging` for monitoring.
- WebSocket token param is `Optional[str] = Query(None)` (not `Query(...)`) so a
  missing token yields our explicit 4001 close instead of FastAPI's generic
  validation close. Tests live in `backend/tests/test_security.py`.

## Implementation Notes

### Backend Changes (main.py)

```python
# Make token validation strict
async def player_websocket(websocket: WebSocket, room_code: str, player_id: str, token: str = Query(...)):
    # token is now required (no default)
    player_conn = room.get_player_connection(player_id)
    if not player_conn or player_conn.session_token != token:
        await websocket.close(code=4001, reason="Invalid session token")
        return
```

### Frontend Changes

- Store token from `/create` or `/join` response
- Include token in WebSocket URL query params
- Include token in Authorization header for REST calls

## Security Considerations

- Tokens should be cryptographically random (current UUID is acceptable)
- Consider token expiration for long-running games
- Log authentication failures for monitoring
